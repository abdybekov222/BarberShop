# Requirements Document

## Introduction

Данный документ описывает требования к функционалу «Админ-панель» — этап 8 дорожной карты разработки премиального сайта барбершопа для Кыргызстана. Админ-панель — это защищённый раздел /admin для ролей owner, admin и master, позволяющий владельцу и администратору салона управлять всем контентом и операциями: услугами и их категориями, мастерами и их расписанием, галереей, записями клиентов, настройками салона. Отдельный раздел «ИИ» даёт owner и admin контроль над ИИ-модулем «Виртуальное зеркало»: аварийный выключатель (Kill Switch), мониторинг бюджета и потолков генераций, каталог стилей, журнал блокировок и ручное начисление ИИ-попыток пользователям. Роль master имеет ограниченный доступ: просмотр своих записей, расписания и галереи.

Вне объёма данного спека: публичные страницы (главная, услуги, галерея, команда, контакты), онлайн-запись виджет (но управление записями — в объёте), логика ИИ-генерации (но управление ИИ — Kill Switch, бюджет, стили, лимиты — в объёте), страница авторизации (но проверка ролей — в объёте). Спек опирается на завершённые или разрабатываемые этапы: Foundation + Auth (монорепозиторий, Prisma-схема, авторизация, RolesGuard), Public Site (публичные страницы, Catalog API), Booking (система записи, движок слотов), AI Mirror (ИИ-генерация, ai_budget, ai_quota_ledger, ai_abuse_log, Kill Switch).

## Glossary

- **Админ-панель**: защищённый раздел /admin веб-клиента, доступный ролям owner, admin и master, для управления контентом, записями и ИИ-модулем.
- **API**: приложение apps/api — бэкенд на NestJS (TypeScript), предоставляющее REST API с документацией OpenAPI/Swagger.
- **Веб-клиент**: приложение apps/web — фронтенд на Next.js 14+ (App Router, TypeScript).
- **packages/shared**: общий пакет монорепозитория, содержащий Zod-схемы, TypeScript-типы и утилиту formatKgs.
- **RolesGuard**: NestJS guard для проверки ролей пользователя при доступе к защищённым эндпоинтам; реализован на этапе Foundation + Auth.
- **owner**: роль с полным доступом ко всем разделам админ-панели, включая бюджет ИИ, Kill Switch и ручное начисление попыток.
- **admin**: роль с доступом к управлению контентом (услуги, мастера, расписание, галерея, записи) и просмотру раздела «ИИ»; без права ручного начисления попыток и без права управления бюджетом и потолками.
- **master**: роль с ограниченным доступом — просмотр своих записей, расписания и галереи; без прав редактирования контента салона.
- **client**: роль обычного пользователя; не имеет доступа к админ-панели.
- **Kill Switch**: аварийный выключатель ИИ-модуля — флаг kill_switch в таблице ai_budget; при включении ИИ-зеркало скрывается с сайта, загрузка и генерация блокируются.
- **kill_reason**: причина последнего отключения ИИ — enum (manual, budget, daily_cap, provider_errors) в таблице ai_budget.
- **ai_budget**: таблица с одной строкой, хранящая бюджет ИИ (budget_usd, spent_usd, reserved_usd), потолки (hourly_cap, daily_cap) и состояние Kill Switch.
- **hourly_cap**: потолок генераций в час на весь сайт — поле в ai_budget.
- **daily_cap**: потолок генераций в сутки на весь сайт — поле в ai_budget.
- **ai_abuse_log**: таблица-журнал блокировок антифрода; доступна только для чтения в админ-панели.
- **ai_quota_ledger**: таблица-журнал аудита квот ИИ; только добавление записей (append-only).
- **admin_grant**: причина записи в ai_quota_ledger при ручном начислении бонусных ИИ-попыток администратором.
- **ai_quotas**: таблица лимитов ИИ-генераций пользователя; содержит free_limit, used_count, bonus_count; остаток = free_limit + bonus_count − used_count.
- **bonus_count**: поле в ai_quotas — зарезервированные дополнительные (платные/промо) попытки; увеличивается при admin_grant.
- **hair_styles**: таблица каталога ИИ-образов (12–20 штук); тип haircut, beard или combo; содержит prompt, seed, model_params.
- **salon_settings**: таблица ключ-значение для настроек салона (часовой пояс, шаг слотов, лимиты ИИ и др.).
- **master_services**: таблица связи мастера и услуги с индивидуальными ценой и длительностью (price_override, duration_override).
- **working_hours**: таблица рабочих часов мастера по дням недели (weekday 0–6).
- **time_off**: таблица отсутствий мастера (отпуск, больничный, исключение).
- **gallery_items**: таблица элементов галереи работ с привязкой к мастеру и категории.
- **booking_items**: таблица снимка услуг в записи (price, duration_min на момент записи).
- **confirmed_by**: поле в bookings — FK на users; администратор, подтвердивший запись Google-пользователя без SMS-верификации.
- **formatKgs**: функция в packages/shared, форматирующая целочисленную цену в строку вида «1 200 сом».
- **Zod-схема**: схема валидации на стороне API и Веб-клиента, определённая в packages/shared.
- **S3-хранилище**: S3-совместимое хранилище для фото галереи; доступ по подписанным URL.
- **E2E-тест**: сквозной тест на Playwright, проверяющий пользовательский сценарий в админ-панели.

## Requirements

### Requirement 1: Защита маршрутов /admin и проверка ролей

**User Story:** Как владелец салона, я хочу, чтобы раздел /admin был доступен только авторизованным пользователям с ролями owner, admin или master, чтобы предотвратить доступ посторонних к управлению салоном.

#### Acceptance Criteria

1. WHEN неавторизованный пользователь открывает любой маршрут /admin, THE Веб-клиент SHALL перенаправить пользователя на страницу /auth.
2. WHEN пользователь с ролью client открывает любой маршрут /admin, THE API SHALL отклонить запрос с кодом 403.
3. WHEN пользователь с ролью master открывает маршрут управления услугами, мастерами или настройками салона, THE API SHALL отклонить запрос с кодом 403.
4. THE API SHALL проверять роль пользователя через RolesGuard на каждом эндпоинте /admin/* перед выполнением бизнес-логики.
5. THE Веб-клиент SHALL скрывать пункты навигации админ-панели, недоступные текущей роли пользователя.
6. WHILE пользователь с ролью master авторизован, THE Веб-клиент SHALL отображать только разделы «Мои записи», «Расписание» и «Галерея», относящиеся к этому мастеру.

### Requirement 2: Матрица доступа по ролям

**User Story:** Как администратор салона, я хочу чёткую матрицу прав доступа, чтобы каждая роль видела и могла выполнять только разрешённые действия.

#### Acceptance Criteria

1. THE Роль owner SHALL иметь доступ ко всем разделам админ-панели, включая бюджет ИИ, Kill Switch, потолки генераций и ручное начисление попыток.
2. THE Роль admin SHALL иметь доступ к управлению услугами, категориями, мастерами, расписанием, галереей, записями, настройками салона и просмотру раздела «ИИ».
3. THE Роль admin SHALL быть лишена права ручного начисления ИИ-попыток, изменения Kill Switch и редактирования потолков генераций.
4. THE Роль master SHALL видеть только записи, расписание и элементы галереи, привязанные к этому мастеру.
5. IF пользователь с ролью admin обращается к эндпоинту ручного начисления попыток, THEN THE RolesGuard SHALL отклонить запрос с кодом 403.
6. IF пользователь с ролью master обращается к эндпоинту CRUD услуг или настроек салона, THEN THE RolesGuard SHALL отклонить запрос с кодом 403.

### Requirement 3: CRUD категорий услуг

**User Story:** Как администратор, я хочу создавать, редактировать, удалять и упорядочивать категории услуг, чтобы управлять структурой прайс-листа салона.

#### Acceptance Criteria

1. WHEN администратор создаёт категорию, THE API SHALL сохранить запись в service_categories с полями slug, name и sort_order.
2. THE API SHALL обеспечивать уникальность slug в таблице service_categories.
3. WHEN администратор обновляет категорию, THE API SHALL сохранить изменения полей name и sort_order.
4. WHEN администратор удаляет категорию, THE API SHALL проверить отсутствие привязанных услуг и удалить запись, либо отклонить удаление с кодом 409, если услуги существуют.
5. THE API SHALL возвращать список категорий, отсортированный по sort_order.
6. THE API SHALL валидировать входные данные категории через Zod-схему в packages/shared перед сохранением.

### Requirement 4: CRUD услуг

**User Story:** Как администратор, я хочу создавать, редактировать, удалять и управлять услугами салона, чтобы поддерживать актуальный прайс-лист.

#### Acceptance Criteria

1. WHEN администратор создаёт услугу, THE API SHALL сохранить запись в services с полями category_id (FK), name, description, base_price, price_is_from, duration_min, is_combo, is_active и sort_order.
2. THE API SHALL хранить base_price как целое число в сомах (KGS) в поле numeric(10,0).
3. WHEN администратор обновляет услугу, THE API SHALL сохранить изменения полей name, description, base_price, price_is_from, duration_min, is_combo, is_active и sort_order.
4. WHEN администратор деактивирует услугу (is_active = false), THE API SHALL сохранять запись в базе данных и услуга SHALL перестать отображаться в публичном каталоге.
5. WHEN администратор удаляет услугу, THE API SHALL проверить отсутствие активных записей, содержащих эту услугу, и удалить запись, либо отклонить удаление с кодом 409.
6. THE API SHALL возвращать список услуг с возможностью фильтрации по category_id и is_active.
7. THE API SHALL валидировать, что base_price является неотрицательным целым числом.
8. THE Веб-клиент SHALL отображать цену услуги через formatKgs в формате «N сом».

### Requirement 5: CRUD мастеров

**User Story:** Как администратор, я хочу создавать, редактировать, удалять и управлять профилями мастеров, чтобы поддерживать актуальную команду салона.

#### Acceptance Criteria

1. WHEN администратор создаёт мастера, THE API SHALL сохранить запись в masters с полями slug, name, rank, bio, experience_years, photo_url, specialties, is_active и sort_order.
2. THE API SHALL обеспечивать уникальность slug в таблице masters.
3. THE API SHALL принимать значение rank только из enum (chief, top, senior, barber).
4. WHEN администратор обновляет мастера, THE API SHALL сохранить изменения полей name, rank, bio, experience_years, photo_url, specialties, is_active и sort_order.
5. WHEN администратор деактивирует мастера (is_active = false), THE API SHALL сохранять запись в базе данных и мастер SHALL перестать отображаться на публичном сайте и в списке доступных для записи.
6. WHEN администратор удаляет мастера, THE API SHALL проверить отсутствие активных записей и рабочего расписания, и удалить запись, либо отклонить удаление с кодом 409.
7. THE API SHALL позволять опционально привязать мастера к учётной записи пользователя через поле user_id.
8. THE API SHALL возвращать список мастеров, отсортированный по rank и sort_order.

### Requirement 6: Управление услугами мастера (master_services)

**User Story:** Как администратор, я хочу назначать услуги конкретным мастерам с индивидуальными ценами и длительностью, чтобы отражать реальную специализацию и тарифы каждого барбера.

#### Acceptance Criteria

1. WHEN администратор назначает услугу мастеру, THE API SHALL создать или обновить запись в master_services с полями master_id, service_id, price_override и duration_override.
2. THE API SHALL обеспечивать уникальность пары (master_id, service_id) как первичного ключа в master_services.
3. WHERE price_override не указан, THE API SHALL использовать base_price из services при отображении и расчёте записи.
4. WHERE duration_override не указан, THE API SHALL использовать duration_min из services при отображении и расчёте записи.
5. WHEN администратор удаляет назначение услуги мастеру, THE API SHALL удалить запись из master_services и проверить отсутствие будущих записей с этой парой мастер-услуга.
6. THE API SHALL возвращать список услуг конкретного мастера с итоговыми ценами и длительностью с учётом переопределений.
7. THE API SHALL валидировать, что price_override, если указан, является неотрицательным целым числом в сомах (KGS).

### Requirement 7: CRUD рабочих часов мастера (working_hours)

**User Story:** Как администратор, я хочу управлять рабочими часами мастеров по дням недели, чтобы система корректно формировала доступные слоты для записи.

#### Acceptance Criteria

1. WHEN администратор создаёт рабочие часы, THE API SHALL сохранить запись в working_hours с полями master_id, weekday (0–6), start_time, end_time, break_start и break_end.
2. THE API SHALL валидировать, что weekday находится в диапазоне от 0 до 6.
3. THE API SHALL валидировать, что start_time меньше end_time в течение одного дня.
4. WHERE указаны break_start и break_end, THE API SHALL валидировать, что перерыв находится в пределах рабочего времени (start_time ≤ break_start < break_end ≤ end_time).
5. WHEN администратор обновляет рабочие часы, THE API SHALL сохранить изменения полей weekday, start_time, end_time, break_start и break_end.
6. WHEN администратор удаляет рабочие часы, THE API SHALL удалить запись из working_hours.
7. THE API SHALL возвращать рабочие часы мастера, сгруппированные по weekday.

### Requirement 8: CRUD отсутствий мастера (time_off)

**User Story:** Как администратор, я хочу управлять отсутствиями мастеров (отпуск, больничный, исключения), чтобы слоты в эти периоды не были доступны для записи.

#### Acceptance Criteria

1. WHEN администратор создаёт отсутствие, THE API SHALL сохранить запись в time_off с полями master_id, starts_at, ends_at и reason.
2. THE API SHALL валидировать, что starts_at меньше ends_at.
3. THE API SHALL принимать значение reason из набора: отпуск, больничный, исключение.
4. WHEN администратор обновляет отсутствие, THE API SHALL сохранить изменения полей starts_at, ends_at и reason.
5. WHEN администратор удаляет отсутствие, THE API SHALL удалить запись из time_off.
6. THE API SHALL хранить starts_at и ends_at в UTC, а отображать в часовом поясе Asia/Bishbek в Веб-клиенте.
7. THE API SHALL возвращать отсутствия мастера с возможностью фильтрации по диапазону дат.

### Requirement 9: CRUD элементов галереи

**User Story:** Как администратор, я хочу загружать, редактировать, публиковать и удалять фотографии работ в галерее, чтобы демонстрировать клиентам качество услуг салона.

#### Acceptance Criteria

1. WHEN администратор загружает изображение, THE API SHALL сохранить файл в S3-хранилище и создать запись в gallery_items с полями master_id, service_category_id, style_tag, image_url, width, height, blurhash, caption, is_published и sort_order.
2. THE API SHALL принимать изображения в форматах AVIF и WebP для оптимизации.
3. WHEN администратор обновляет элемент галереи, THE API SHALL сохранить изменения полей master_id, service_category_id, style_tag, caption, is_published и sort_order.
4. WHEN администратор публикует элемент (is_published = true), THE API SHALL отображать элемент в публичной галерее.
5. WHEN администратор снимает с публикации элемент (is_published = false), THE API SHALL скрыть элемент из публичной галереи, сохранив запись в базе данных.
6. WHEN администратор удаляет элемент галереи, THE API SHALL удалить файл из S3-хранилища и запись из gallery_items.
7. THE API SHALL возвращать список элементов галереи с возможностью фильтрации по master_id, service_category_id и is_published.
8. THE API SHALL генерировать blurhash для загруженного изображения и сохранять его в базе данных.

### Requirement 10: Управление записями — просмотр и фильтрация

**User Story:** Как администратор, я хочу просматривать все записи салона с фильтрами по мастеру, дате и статусу, чтобы контролировать загрузку и оперативно реагировать на изменения.

#### Acceptance Criteria

1. THE API SHALL возвращать список всех записей с возможностью фильтрации по master_id, диапазону дат и status.
2. THE API SHALL возвращать детали записи, включая список booking_items с услугами, ценами и длительностью.
3. THE API SHALL возвращать в деталях записи информацию о клиенте (имя, телефон) и источнике записи (web, admin, telegram).
4. WHILE пользователь с ролью master просматривает записи, THE API SHALL возвращать только записи, где master_id соответствует этому мастеру.
5. THE API SHALL возвращать записи с пагинацией и сортировкой по starts_at.
6. THE API SHALL отображать total_price в сомах (KGS), а Веб-клиент SHALL форматировать через formatKgs.

### Requirement 11: Управление записями — изменение статуса

**User Story:** Как администратор, я хочу изменять статус записей (подтвердить, завершить, отменить, отметить неявку), чтобы отражать реальное состояние визитов клиентов.

#### Acceptance Criteria

1. WHEN администратор подтверждает запись, THE API SHALL изменить status на confirmed и записать confirmed_by — идентификатор администратора.
2. WHEN администратор завершает запись, THE API SHALL изменить status на completed.
3. WHEN администратор отменяет запись салоном, THE API SHALL изменить status на cancelled_by_salon, записать cancelled_at и cancel_reason.
4. WHEN администратор отмечает неявку клиента, THE API SHALL изменить status на no_show.
5. THE API SHALL принимать изменение статуса только для значений из enum (confirmed, completed, cancelled_by_salon, no_show).
6. IF запись уже имеет терминальный статус (completed, cancelled_by_salon, no_show), THEN THE API SHALL отклонить изменение статуса с кодом 409.
7. THE API SHALL логировать каждое изменение статуса записи с указанием администратора, прежнего и нового статуса и времени.

### Requirement 12: Управление записями — подтверждение записей Google-пользователей

**User Story:** Как администратор, я хочу подтверждать записи, созданные Google-пользователями без SMS-верификации, чтобы салон мог ручно подтвердить визит клиента.

#### Acceptance Criteria

1. WHEN администратор подтверждает запись Google-пользователя, THE API SHALL заполнить поле confirmed_by идентификатором этого администратора.
2. THE API SHALL отображать в списке записей признак необходимости подтверждения для записей Google-пользователей без confirmed_by.
3. THE Веб-клиент SHALL отображать записи, ожидающие подтверждения, с выделением и кнопкой «Подтвердить».
4. THE API SHALL обеспечивать, что только пользователь с ролью admin или owner может подтвердить запись.

### Requirement 13: Экспорт списка записей

**User Story:** Как владелец салона, я хочу экспортировать список записей, чтобы анализировать загрузку мастеров вне системы.

#### Acceptance Criteria

1. WHEN администратор запрашивает экспорт записей с фильтрами, THE API SHALL вернуть файл в формате CSV с колонками: дата, время, мастер, клиент, услуги, цена, статус.
2. THE API SHALL применять те же фильтры (master_id, диапазон дат, status) к экспортируемым записям, что и к списку.

### Requirement 15: Раздел «ИИ» — Kill Switch (аварийный выключатель)

### Requirement 16: Раздел «ИИ» — мониторинг бюджета

3. THE API SHALL возвращать число генераций за текущий час и за текущие сутки, рассчитанное из ai_generations с учётом часового пояса Asia/Bishkek.
4. THE API SHALL возвращать расход в долларах за текущий час и за текущие сутки, рассчитанный как сумму cost_usd из ai_generations.

6. THE API SHALL отклонять доступ к эндпоинту бюджета для роли master с кодом 403.
7. THE Веб-клиент SHALL отображать бюджет в долларах (USD) с указанием потраченной, зарезервированной и оставшейся суммы.

### Requirement 18: Раздел «ИИ» — CRUD каталога стилей

### Requirement 20: Раздел «ИИ» — ручное начисление попыток (admin_grant)

**User Story:** Как владелец салона, я хочу вручную начислять дополнительные ИИ-попытки конкретным пользователям, чтобы поощрять лояльных клиентов или компенсировать сбои.

#### Acceptance Criteria

1. WHEN пользователь с ролью owner или admin отправляет запрос на начисление попыток, THE API SHALL увеличить bonus_count в ai_quotas указанного пользователя на заданное количество.
2. THE API SHALL создать запись в ai_quota_ledger с delta равным начисленному количеству, reason = admin_grant и balance_after, равным новому остатку (free_limit + bonus_count − used_count).
3. THE API SHALL записывать в ai_quota_ledger идентификатор администратора, выполнившего начисление, идентификатор пользователя-получателя, количество и время начисления.
4. THE API SHALL валидировать, что количество начисляемых попыток является положительным целым числом.
5. IF пользователь с ролью master обращается к эндпоинту начисления попыток, THEN THE RolesGuard SHALL отклонить запрос с кодом 403.
6. THE API SHALL обеспечивать, что каждое начисление атомарно: обновление bonus_count и запись в ai_quota_ledger выполняются в одной транзакции.
7. THE API SHALL обеспечивать, что таблица ai_quota_ledger является append-only: записи нельзя изменять или удалять.
8. THE API SHALL отклонять начисление попыток заблокированному пользователю (is_blocked = true) с кодом 403.
